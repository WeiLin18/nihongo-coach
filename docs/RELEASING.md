# Releasing

> **中文摘要**
>
> 發版大部分已自動化，一個人維護也能每次照同樣步驟做：
>
> 1. 功能開 feature branch，用 PR 合進 `main`。每個 PR 和 `main` 都會跑 CI（lint、型別檢查、build、音高檢查、migration 編號檢查）。
> 2. 發版：在乾淨、已同步的 `main` 上跑 `npm run release -- minor`（或 `patch` / `major`）。腳本會更新版號、把 CHANGELOG 的 `[Unreleased]` 移到新版本標題下、commit、打 tag，問過你之後才 push。先用 `--dry-run` 看會改什麼。
> 3. tag 推上去後，GitHub Actions 的 Release workflow 會建立 GitHub Release，並等你在 `production` environment 按核准，才記錄 D1 還原點、套用 migration、部署 Worker。
> 4. CI 不會匯出資料庫：repo 是公開的，Actions 的 log 和 artifact 任何人都看得到。要備份就在本機跑 `npm run backup`（存到 git-ignored 的 `backups/`）。CI 只記錄 D1 Time Travel 的時間點，需要時用它還原。
> 5. 修舊版用 `release/x.y` 分支，在上面跑 `npm run release -- patch`。比線上版本舊的 tag 只會建立 Release，不會部署。
> 6. 回滾：Worker 用 `npx wrangler rollback`；migration 只往前，不回滾，要修就加新的 migration，真的壞資料才用 Time Travel 還原。
> 7. D1 免費方案每天最多寫入 10 萬列，大量匯入不要和發版同一天。
> 8. 第一次使用前要建一個 Cloudflare API token，並在 GitHub 設兩個 secret，見最後的 [One-time setup](#one-time-setup)。

This is a solo project, so the flow is small: one long-lived branch (`main`), a tag per release, and a GitHub Actions workflow that deploys the tag.

```
feature branch ──PR──▶ main ──npm run release──▶ commit "Release vX.Y.Z" + tag vX.Y.Z ──push──▶
   CI on every PR       CI          (local, asks before push)

Release workflow (on the tag):  verify ──▶ GitHub Release
                                       └──▶ [approve production] ──▶ D1 restore point ──▶ migrations ──▶ wrangler deploy
```

## Versioning

Versions follow [Semantic Versioning](https://semver.org/) and are recorded in [CHANGELOG.md](../CHANGELOG.md), `package.json` and the version line at the top of both READMEs. `npm run release` updates all of them.

While the version is `0.x`:

- **Minor** (`0.4.0`): a new feature or a set of features, a new D1 migration, or a breaking API change (for example, `/api/cards` changing shape in 0.2.0).
- **Patch** (`0.3.1`): bug fixes and copy or style changes, with no migration and no API change.

After `1.0.0`, a breaking API change (the routes used by the iOS Shortcuts, `/jp` and the MCP connector) needs a major version.

## Branches

- **Feature branches** (`feat/review-heatmap`, `fix/reading-dupes`, or the `claude/…` branches that Claude Code makes) → pull request into `main`. Merge when CI is green and you have tried it locally or in demo mode.
- **`main`** is always deployable. Don't commit half-finished features to it; keep them on their branch. Every PR adds its user-facing changes to the `## [Unreleased]` section of `CHANGELOG.md`.
- **`release/x.y`** branches are only for fixing an older version. See [Hotfixes](#hotfixes-on-releasexy).

## CI

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every pull request and on pushes to `main` and `release/**`. Run the same checks locally with:

```bash
npm run check   # = lint, tsc -b + vite build, scripts/check-pitch.ts, scripts/check-migrations.ts
```

CI uses no secrets, so it also runs safely on pull requests from forks.

## Database migrations

Migrations live in `migrations/` and are generated by drizzle-kit (`npm run db:generate`) from `worker/db/schema.ts`. Wrangler applies them in file-name order and records each one in the `d1_migrations` table.

**Numbering.** Two branches made in parallel will both generate the next free number. This happened in 0.3.0: the SRS branch and the conversation-practice branch both made `0001_…`, and the SRS migration had to be regenerated as `0004_srs`. `scripts/check-migrations.ts` (part of CI) now fails when two files share a number or the files and `meta/_journal.json` disagree. To fix it:

1. Rebase or merge `main` into your branch.
2. Delete your migration file and its snapshot, and remove its entry from `meta/_journal.json`, then run `npm run db:generate` again. Drizzle makes the next number and an up-to-date snapshot. Don't rename the files by hand.
3. Never edit or renumber a migration that has already been applied to the remote database. Add a new one instead.

**Forward only.** There are no down migrations. Write migrations that only add tables, columns and indexes, so the Worker that is still running keeps working while the deploy finishes, and so a Worker rollback still works against the new schema.

**Write limit.** The D1 free plan allows 100,000 rows written per day (reset at 00:00 UTC, 09:00 in Japan). Normal use writes a few rows per card or review, but a large backfill or a re-import of the accent dictionary (about 320k rows) uses up the day's limit, and every write after it fails until the reset. Keep data imports out of release deploys. If a migration rewrites a big table, release early in the UTC day or check the usage in the Cloudflare dashboard first.

## Cutting a release

### 1. Check what will ship

```bash
git switch main && git pull
npm run release -- minor --dry-run      # or patch / major / an exact 0.4.0
```

The dry run checks that the tree is clean, that you are on `main` and level with `origin/main`, that the tag doesn't exist yet and that `[Unreleased]` is not empty. Then it runs `npm run check` and prints the new CHANGELOG section and links. It writes nothing.

Before you release, read the `[Unreleased]` section and tidy it: it becomes the GitHub Release notes as written. If the release changes what the app looks like, update the screenshots in `docs/images/` from demo mode (`npm run demo`) in a PR first.

### 2. Release

```bash
npm run release -- minor
```

The script:

1. Runs `npm run check` (skip with `--skip-checks` if CI is already green on this commit).
2. Sets the version in `package.json`, `package-lock.json` and the README version lines.
3. Moves the `[Unreleased]` items under `## [0.4.0] - YYYY-MM-DD`, leaves an empty `[Unreleased]`, and updates the compare links at the bottom.
4. Commits `Release v0.4.0` and makes the annotated tag `v0.4.0`.
5. Asks `Push main and v0.4.0 to origin?`. Answer `y` to push both in one atomic push. Answer anything else to stop; it prints how to push later or undo (`git tag -d v0.4.0 && git reset --hard HEAD~1`).

The release commit goes straight onto `main`. If you protect `main` with a "require a pull request" rule, allow yourself to bypass it, or the push is refused.

### 3. Approve the deploy

The tag push starts [`.github/workflows/release.yml`](../.github/workflows/release.yml):

| Job | What it does |
| --- | --- |
| `verify` | The same checks as CI. Fails if the tag doesn't match `package.json` or the CHANGELOG has no section for the version. Works out whether this tag is the newest version. |
| `release` | Creates the GitHub Release `v0.4.0` with the CHANGELOG section as notes (or updates the notes when the job is re-run). |
| `deploy` | Waits for your approval on the `production` environment. Then records a D1 Time Travel restore point in the job summary, lists and applies pending remote migrations, and runs `npm run deploy`. Only runs when the tag is the newest version tag. |

Open **Actions → Release → v0.4.0**, check `verify`, and click **Review deployments → production → Approve and deploy**.

The deploy log hides the `*.workers.dev` URL, because Actions logs are public.

### 4. Check

- Open the app on the phone. A PWA update can need one reload, or closing and reopening the app.
- Make one card, open 練習 and 複習, and check that nothing errors.
- Run an iOS Shortcut or `/jp` once if the release touched `/api/ask` or `/api/cards`.

## Backups

The workflow never exports the database. A `wrangler d1 export` contains your real cards and practice history, and in a public repo every Actions log and artifact is readable by anyone. Encrypting an export and uploading it somewhere private is possible, but D1 Time Travel already covers what a pre-deploy backup is for:

- **Time Travel** keeps a point-in-time history of the database (7 days on the Workers Free plan, 30 days on Workers Paid). The `deploy` job writes the time and bookmark just before the migrations into the job summary. Neither contains any data.
- **A local export** is your second copy, kept on your machine. Take one before a release with a risky migration:

  ```bash
  npm run backup   # = wrangler d1 export … --remote → backups/nihongo-coach-YYYYMMDD-HHMM.sql
  ```

  `backups/` is git-ignored. The export includes the accent dictionary, so it is large.

## Hotfixes on `release/x.y`

Use this only when `main` has unreleased work you don't want to ship yet, or to patch an older line.

```bash
git switch -c release/0.4 v0.4.0     # once per minor line
git push -u origin release/0.4
# fix (directly or through a PR into release/0.4), and add it under [Unreleased] in CHANGELOG.md
npm run release -- patch             # → v0.4.1, refuses anything but 0.4.x on this branch
```

Then bring the fix back to `main` with `git cherry-pick` (or merge `release/0.4` into `main`). Move its CHANGELOG entry into the right place on `main` by hand; the release sections will conflict otherwise.

The workflow only deploys a tag that is the newest version tag. If `main` has already released `v0.5.0`, tagging `v0.4.1` creates the GitHub Release (not marked "latest") and skips `deploy`, so production is never downgraded.

## Rolling back

### Worker

```bash
npx wrangler deployments list     # find the version that was live before
npx wrangler rollback             # back to the previous deployment (or: wrangler rollback <version-id>)
```

This only swaps the Worker code and static assets. It doesn't touch D1. Because migrations only add things, the older Worker keeps working on the newer schema.

Fix forward afterwards: fix on `main` and release a new patch. Don't delete or move the bad tag; the next release supersedes it.

### Database

Migrations are forward-only. To undo a schema change, add a new migration that reverses it and release it.

Restore data only when a migration or a bug damaged it. Restoring throws away every write made after the restore point:

```bash
npx wrangler d1 time-travel restore nihongo-coach --timestamp=<time from the deploy job summary>
```

[Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) restores the whole database. Run `npx wrangler rollback` too if the Worker you are keeping needs the newer schema. Your `backups/` export is the last resort; loading it means dropping the tables first.

## When a deploy fails halfway

The `deploy` job runs restore point → migrations → Worker deploy. Look at which step failed:

- **Before `Apply migrations`** (auth error, wrangler error): nothing changed. Fix the cause (usually the token or a secret, see setup) and click **Re-run failed jobs**.
- **During `Apply migrations`**: wrangler applies the files in order and records each one that finished in `d1_migrations`. Earlier migrations stay applied; check in the D1 console whether the failed file left part of its statements behind. Production is still running the old Worker, which works on the partly migrated schema. Check `npx wrangler d1 migrations list nihongo-coach --remote`. If the migration is wrong, fix it in a new commit, release a new patch, and approve that. If it was a temporary failure (or the daily write limit), re-run the failed job.
- **During `Build and deploy the Worker`**: the migrations are in, the old Worker is still live. Re-run the failed job; `migrations apply` has nothing left to do, so it goes straight to the deploy.
- **After a successful deploy, the app is broken**: `npx wrangler rollback` first, then fix forward.

Re-running is safe: the `release` job updates the existing GitHub Release, and the migration step skips migrations that are already applied.

### Deploying without GitHub Actions

If Actions is down, deploy the tag from your machine (needs `npx wrangler login`):

```bash
git switch --detach v0.4.0 && npm ci
npm run backup
npx wrangler d1 migrations list nihongo-coach --remote
npm run db:migrate:remote
npm run deploy
git switch main
```

## One-time setup

Already done in the repo settings: the `production` environment, with you as the required reviewer and only `v*.*.*` tags allowed to deploy.

What is left is two secrets on that environment:

1. **Cloudflare API token.** Cloudflare dashboard → **My Profile → API Tokens → Create Token → Create Custom Token**. Give it two **Account** permissions, **Workers Scripts → Edit** and **D1 → Edit**, and under Account resources include only your account. Copy the token.
2. **Store both secrets.** Each command asks for the value, so it never lands in your shell history:

   ```bash
   gh secret set CLOUDFLARE_API_TOKEN --env production -R WeiLin18/nihongo-coach
   ```

   ```bash
   gh secret set CLOUDFLARE_ACCOUNT_ID --env production -R WeiLin18/nihongo-coach
   ```

   The account ID is shown by `npx wrangler whoami`.

If the first deploy fails with an authentication error that mentions memberships or user details, add **Account Settings → Read** to the token.

The Worker's own secrets (`OPENAI_API_KEY`, `APP_TOKEN`, `MCP_TOKEN`, Azure keys) stay in Cloudflare (`wrangler secret put`). `wrangler deploy` keeps them, and GitHub never needs them.
