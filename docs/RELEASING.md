# Releasing

> **中文摘要**
>
> 一個人維護的專案，流程盡量簡單：
>
> 1. 每個功能開 feature branch，用 PR 合進 `main`。`main` 隨時可以部署。
> 2. 要發版時，在 `main` 上更新 `CHANGELOG.md` 和 `package.json` 的版本，合進 `main`。
> 3. 在那個 commit 打 tag `vX.Y.Z` 並 push，再用 changelog 那一段建立 GitHub Release。平常不需要 `release/x.y` 分支，只有要修舊版時才開。
> 4. 從 tag 部署：先 `wrangler d1 export` 備份遠端 D1 → `migrations apply --remote` → `npm run deploy`。
> 5. Migration 編號在合併前要確認沒有撞號（之前 SRS 和會話練習都用了 0001）；有撞就在合併時重新產生成下一個號碼。
> 6. D1 免費方案每天最多寫入 10 萬列。大量寫入（例如重音字典匯入）會讓當天剩下的寫入被擋到 00:00 UTC（日本時間 09:00），不要在發版當天做。

This is a solo project, so the flow is kept small: one long-lived branch (`main`), tags for releases, and deploys from tags.

## Versioning

Versions follow [Semantic Versioning](https://semver.org/) and are recorded in [CHANGELOG.md](../CHANGELOG.md) and `package.json`.

While the version is `0.x`:

- **Minor** (`0.4.0`): a new feature or a set of features, a new D1 migration, or a breaking API change (for example, `/api/cards` changing shape in 0.2.0).
- **Patch** (`0.3.1`): bug fixes and copy or style changes, with no migration and no API change.

After `1.0.0`, a breaking API change (the routes used by the iOS Shortcuts, `/jp` and the MCP connector) needs a major version.

## Branches

- **Feature branches** (`feat/review-heatmap`, `fix/reading-dupes`, or the `claude/…` branches that Claude Code makes) → pull request into `main`. Merge when the PR builds and you have tried it locally or in demo mode.
- **`main`** is always deployable. Don't commit half-finished features to it; keep them on their branch.
- **`release/x.y`** branches are optional. You don't need one for a normal release: tag `main`. Cut `release/0.3` from the `v0.3.0` tag only when you need to ship a fix to 0.3 while `main` already has unreleased 0.4 work. Fix on the release branch, tag `v0.3.1` there, then merge or cherry-pick the fix back into `main`.

## Database migrations

Migrations live in `migrations/` and are generated by drizzle-kit (`npm run db:generate`) from `worker/db/schema.ts`. Wrangler applies them in file-name order and records each one in the `d1_migrations` table.

**Numbering.** Two branches made in parallel will both generate the next free number. This happened in 0.3.0: the SRS branch and the conversation-practice branch both made `0001_…`, and the SRS migration had to be regenerated as `0004_srs` when it was merged. To avoid it:

1. Before you merge a branch that adds a migration, check `ls migrations/` on `main`.
2. If the number is taken, rebase or merge `main` into your branch, delete your migration file and its snapshot, and run `npm run db:generate` again. Drizzle then makes the next number and an up-to-date snapshot in `migrations/meta/`. Don't rename the files by hand: the `_journal.json` and the snapshot must match.
3. Never edit or renumber a migration that has already been applied to the remote database. Add a new one instead.

**Write limit.** The D1 free plan allows 100,000 rows written per day (reset at 00:00 UTC, 09:00 in Japan). Normal use writes a few rows per card or review, but a large backfill or a re-import of the accent dictionary (about 320k rows) uses up the day's limit, and every write after it fails until the reset. Keep data imports out of release deploys. If a migration rewrites a big table, run it early in the UTC day or check the usage in the Cloudflare dashboard first.

## Release checklist

Replace `0.4.0` with the version you're releasing.

### 1. Prepare the release on `main`

```bash
git switch main && git pull
npm run lint && npm run build
```

- In `CHANGELOG.md`, rename `## [Unreleased]` to `## [0.4.0] - YYYY-MM-DD`, add a new empty `## [Unreleased]` above it, and add the compare link at the bottom (`[0.4.0]: …/compare/v0.3.0...v0.4.0`).
- Set the version: `npm version 0.4.0 --no-git-tag-version` (updates `package.json` and `package-lock.json`).
- If the release changes what the app looks like, update the screenshots in `docs/images/` from demo mode (`npm run demo`) and both READMEs.

Commit (`Release v0.4.0`) on a branch and merge the PR, or commit directly on `main` if that's how you work.

### 2. Tag

```bash
git switch main && git pull
git tag -a v0.4.0 -m "v0.4.0"
git push origin v0.4.0
```

### 3. GitHub Release

Use the changelog section as the release notes:

```bash
awk '/^## \[0.4.0\]/{f=1;next} /^## \[/{f=0} f' CHANGELOG.md > /tmp/notes.md
gh release create v0.4.0 --title "v0.4.0" --notes-file /tmp/notes.md
```

### 4. Deploy from the tag

Deploy the tagged commit, not whatever is checked out:

```bash
git switch --detach v0.4.0
npm ci
```

Back up the remote database before any migration:

```bash
mkdir -p backups
npx wrangler d1 export nihongo-coach --remote --output "backups/nihongo-coach-$(date +%Y%m%d-%H%M)-pre-v0.4.0.sql"
```

`backups/` holds your real cards: keep it out of git (add it to `.gitignore`, or write the file outside the repo). The export includes the accent dictionary, so it is large.

Then apply migrations and deploy:

```bash
npx wrangler d1 migrations list nihongo-coach --remote    # see what will run
npm run db:migrate:remote                                 # = wrangler d1 migrations apply nihongo-coach --remote
npm run deploy                                            # build + wrangler deploy
git switch main
```

Apply migrations **before** `npm run deploy`, so the new Worker never runs against an old schema. Migrations should only add tables, columns and indexes, so the old Worker keeps working during the few seconds between the two steps.

### 5. Check

- Open the app on the phone. A PWA update can need one reload, or closing and reopening the app.
- Make one card, open 練習 and 複習, and check that nothing errors.
- Run an iOS Shortcut or `/jp` once if the release touched `/api/ask` or `/api/cards`.

### Rolling back

- **Worker only**: `npx wrangler rollback` returns to the previous deployment (see `npx wrangler deployments list`). Or check out the previous tag and run `npm run deploy`.
- **Database**: D1 [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) can restore the database to a point in time (`npx wrangler d1 time-travel restore nihongo-coach --timestamp=<before the migration>`). The `wrangler d1 export` file is your second copy. Restoring the export into the same database means dropping the tables first, so prefer Time Travel.
